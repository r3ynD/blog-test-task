# База данных

Главная уже читает данные из MySQL. PHP-файл с демоданными нужен только для сидинга.
Сейчас есть категории, статьи и связь между ними. Одна статья может относиться
к нескольким категориям. Ниже сначала описана текущая схема, затем — план расширения.

SQL создания таблиц: [001_create_blog.sql](migrations/001_create_blog.sql).
Текущие таблицы используют InnoDB и `utf8mb4`. Поля обязательные, `NULL` не используется.
В Docker используется MySQL 8.4; выборка последних статей на главной требует MySQL 8+.

## categories

| Поле | Тип | Назначение |
| --- | --- | --- |
| id | INT UNSIGNED | Первичный ключ, AUTO_INCREMENT |
| name | VARCHAR(150) | Название категории |
| description | TEXT | Описание категории |
| created_at | DATETIME | Дата создания, по умолчанию CURRENT_TIMESTAMP |

## articles

| Поле | Тип | Назначение |
| --- | --- | --- |
| id | INT UNSIGNED | Первичный ключ, AUTO_INCREMENT |
| image | VARCHAR(255) | Путь или URL изображения |
| title | VARCHAR(255) | Заголовок |
| description | TEXT | Краткое описание для списка статей |
| text | MEDIUMTEXT | Полный текст |
| views | INT UNSIGNED | Просмотры, по умолчанию 0 |
| published_at | DATETIME | Дата публикации для сортировки и последних статей |
| created_at | DATETIME | Дата создания записи, по умолчанию CURRENT_TIMESTAMP |

Дата публикации задаётся отдельно от даты создания записи.

## article_categories

| Поле | Тип | Назначение |
| --- | --- | --- |
| article_id | INT UNSIGNED | Внешний ключ на articles.id |
| category_id | INT UNSIGNED | Внешний ключ на categories.id |

Первичный ключ `(article_id, category_id)` запрещает повторно добавить статью
в ту же категорию. Индекс `(category_id, article_id)` нужен для поиска статей
категории. Первый ключ также позволяет искать категории статьи.

При удалении статьи или категории связанные строки из `article_categories`
удаляются автоматически. Удаление категории не удаляет сами статьи.
Индексы для сортировки добавим при реализации запросов, если план выполнения
покажет, что они нужны.

## Пример связи

Есть две категории: `1 — PHP` и `2 — Базы данных`.
Статья `10 — Как выбрать индекс для запроса` имеет изображение
`/assets/images/database.jpg`, краткое описание, полный текст,
`views = 0` и `published_at = 2026-01-10 12:00:00`.

Чтобы отнести её к обеим категориям, в `article_categories` нужны две строки:

| article_id | category_id |
| --- | --- |
| 10 | 1 |
| 10 | 2 |

Другие статьи из этих категорий могут попасть в блок похожих статей.
По заданному правилу сначала идут статьи с большим числом общих категорий,
затем — более свежие; текущая статья исключается, выводятся максимум три.

## Миграции и проверка

[bin/migrate.php](../bin/migrate.php) применяет SQL-файлы по порядку имён.
В служебной таблице `schema_migrations` хранятся `filename` (VARCHAR(255),
первичный ключ) и `applied_at` (DATETIME, по умолчанию CURRENT_TIMESTAMP).
При повторном запуске уже применённые файлы пропускаются.

[tests/database.php](../tests/database.php) проверяет повторный запуск миграций,
внешние ключи, уникальность связей и каскадное удаление на отдельной тестовой БД.

Демоданные лежат в [seeds/blog.php](seeds/blog.php). Команда `php bin/seed.php`
добавляет 12 статей и 4 категории, только если таблицы категорий и статей пустые.
Одна категория оставлена без статей для проверки главной.

## План: пользователи и роли

Эти таблицы и изменения ещё не добавлены в миграции. Для следующего этапа нужны
три новые таблицы: `roles`, `users`, `comments`, а также автор у статьи.
`schema_migrations` остаётся служебной таблицей.

### roles

| Поле | Тип | Назначение |
| --- | --- | --- |
| id | INT UNSIGNED | Первичный ключ, AUTO_INCREMENT |
| code | VARCHAR(32) | Уникальный код: ROLE_USER, ROLE_WRITER, ROLE_ADMIN |
| name | VARCHAR(64) | Название для админки: Пользователь, Автор, Администратор |

Коды храним строками в справочнике ролей, без MySQL ENUM. Новую роль можно будет
добавить без изменения структуры таблицы. Её права потребуется явно описать в PHP;
неизвестный код сам по себе не даёт доступ к закрытым действиям.

### users

| Поле | Тип | Назначение |
| --- | --- | --- |
| id | INT UNSIGNED | Первичный ключ, AUTO_INCREMENT |
| username | VARCHAR(32) | Уникальный логин для входа |
| name | VARCHAR(100) | Имя, отображаемое у статей и комментариев |
| password_hash | VARCHAR(255) | Хеш пароля, исходный пароль не сохраняется |
| role_id | INT UNSIGNED | Внешний ключ на roles.id |
| created_at | DATETIME | Дата регистрации, по умолчанию CURRENT_TIMESTAMP |

У пользователя одна роль. Например, `role_id = 2` ссылается на строку
`roles.id = 2, code = ROLE_WRITER`. Дополнительная таблица `user_roles` сейчас не нужна.
Роль, на которую ссылаются пользователи, удалять нельзя.

Логин: 3–32 латинские буквы, цифры и `_`, без различия регистра. Перед сохранением
и поиском приводим его к нижнему регистру. Email для этого MVP не требуется.
Пароли обрабатываем через `password_hash()` и `password_verify()`.

Регистрация всегда назначает ROLE_USER на сервере. Выбор роли в запросе регистрации
не принимается. Автора и администратора назначает администратор.
В PHP-сессии достаточно хранить ID пользователя; актуальную роль загружаем из БД,
чтобы её изменение сразу влияло на доступ.

### Автор статьи

В `articles` добавляем `author_id INT UNSIGNED`, внешний ключ на `users.id`.
В итоговой схеме автор обязателен. Профиль автора и его публикации доступны читателям
без входа; список статей выбирается по `author_id`.

При создании статьи автор берётся из сессии. При редактировании проверяем и роль,
и автора существующей записи. Смена роли не удаляет ранее написанные статьи.
Удалять пользователя со статьями или комментариями пока запрещаем внешними ключами.

### comments

| Поле | Тип | Назначение |
| --- | --- | --- |
| id | INT UNSIGNED | Первичный ключ, AUTO_INCREMENT |
| article_id | INT UNSIGNED | Внешний ключ на articles.id |
| user_id | INT UNSIGNED | Внешний ключ на users.id |
| text | TEXT | Текст комментария |
| created_at | DATETIME | Дата добавления, по умолчанию CURRENT_TIMESTAMP |

Комментарии плоские, без ответов и вложенных веток. Текст — от 1 до 2000 символов,
выводится с экранированием, без пользовательского HTML. Пользователь комментария
берётся из сессии. При удалении статьи её комментарии удаляются каскадно.

Пример: статья `10` принадлежит автору `7`; комментарий `31` связывает эту статью
с пользователем `12`. Категории статьи по-прежнему хранятся в `article_categories`.

### Доступ

| Кто | Что доступно |
| --- | --- |
| Гость | Читать статьи, категории и профили авторов |
| ROLE_USER | То же, плюс оставлять комментарии |
| ROLE_WRITER | То же, плюс создавать статьи и изменять свои |
| ROLE_ADMIN | Изменять любые статьи и назначать роли |

Администратор также может публиковать собственные статьи и комментировать.
Все ограничения проверяются на сервере. Скрытая кнопка в меню не заменяет проверку
в обработчике запроса. Формы защищаем CSRF-токенами; значения SQL передаём параметрами.
Нельзя понизить роль последнего администратора. Первый администратор создаётся
отдельной CLI-командой; его пароль не попадает в сиды или репозиторий.

## План: списки, пагинация и индексы

Списки статей категории и автора — по 6 записей на страницу, комментарии и список
статей в админке — по 10. Размер фиксированный. `page` — положительное целое число;
неизвестная сортировка возвращается к сортировке по дате. Ссылки пагинации сохраняют
выбранную сортировку. Число страниц считаем отдельным COUNT с теми же фильтрами.

Порядок по дате: `published_at DESC, id DESC`.
Порядок по просмотрам: `views DESC, published_at DESC, id DESC`.
Комментарии: `created_at ASC, id ASC`. ID задаёт порядок при совпадении дат или просмотров.
Столбцы сортировки выбираются только из явного списка в PHP.

| Индекс | Для какого запроса |
| --- | --- |
| roles: UNIQUE(code) | Поиск роли по коду, запрет дублей |
| users: UNIQUE(username) | Вход и запрет повторяющихся логинов |
| users: (role_id) | Внешний ключ пользователя на роль |
| articles: (author_id, published_at, id) | Статьи автора по дате, внешний ключ автора |
| articles: (published_at, id) | Общий список статей в админке по дате |
| articles: (views, published_at, id) | Общий блок популярных статей |
| comments: (article_id, created_at, id) | Комментарии статьи по страницам, внешний ключ статьи |
| comments: (user_id) | Внешний ключ комментария на пользователя |

Существующие ключи `article_categories` сохраняем. Индексы выше — план под конкретные
будущие запросы; перед добавлением проверим их через EXPLAIN. Индекс просмотров
для общего списка не гарантирует такой же выигрыш при фильтрации по категории:
там есть JOIN, и его план нужно смотреть отдельно.

## План: главная и меню

В шапке оставляем название блога и переключатель темы, добавляем ссылки «Главная»
и «Категории». Для гостя — «Войти» и «Регистрация», после входа — профиль и выход.
Автору показываем «Мои статьи», администратору — «Админка».
На узком экране меню переносится на следующую строку.

На главной добавляем небольшой блок из 3 популярных статей, отсортированных
по просмотрам, дате и ID. Блоки категорий с 3 последними статьями сохраняем:
это обязательная часть исходного задания. Сами короткие блоки главной не пагинируются;
пагинация нужна на страницах полных списков.

## План: когда засчитывать просмотр

Поле `articles.views` уже есть. Сейчас в нём демонстрационные значения из сида;
подсчёт реальных просмотров ещё не реализован.

Для первой версии предлагается порог 30 секунд видимого чтения страницы статьи.
Время в фоновой вкладке не учитывается. Для длинного текста нужна хотя бы одна
прокрутка; если весь текст помещается на экране, прокрутка не требуется.

JavaScript после выполнения условий отправляет POST с ID статьи и CSRF-токеном.
Сервер проверяет статью, токен, время с её открытия и отметку в PHP-сессии.
На одну статью засчитываем максимум один просмотр за сессию, независимо от входа
в аккаунт. Счётчик увеличиваем атомарно: `views = views + 1`.
Обычный GET страницы ничего не прибавляет.

Это приблизительный счётчик чтения, а не точная статистика уникальных посетителей:
сервер не может проверить внимание читателя, а новая сессия позволит засчитать
повторный просмотр. Отдельная таблица событий просмотров для MVP не требуется.

Вариант с порогом `max(30, ceil(число_символов / 15))` можно обсудить отдельно.
Для него нужно согласовать скорость чтения; зависимость от категории неоднозначна,
поскольку у статьи может быть несколько категорий. Пока фиксируем простой порог,
без коэффициентов по темам и настроек в админке.

## Как перейти с текущей схемы

Существующую миграцию не переписываем, таблицы и статьи не пересоздаём.
Сначала новой миграцией добавляем роли, пользователей, комментарии и временно
допускающий NULL `articles.author_id`. Затем создаём реального администратора
и назначаем автора уже существующим демостатьям. После заполнения всех авторов
отдельной миграцией делаем поле обязательным.

Сид новых статей тоже должен указывать автора. Окончательную миграцию с NOT NULL
добавляем после назначения авторов, чтобы текущий запуск всех миграций по порядку
не упал на уже заполненной базе.
